## 一、两张表分别存什么？靠哪个字段关联？

| 表 | 存什么 | 一行代表 |
|---|---|---|
| **`notes`** | 笔记本体：正文、创建时间 | 一条笔记 |
| **`note_tags`** | 哪条笔记有哪些标签、标签的顺序 | **一个标签**（一条笔记有 N 个标签就有 N 行） |

**关联字段是 `note_tags.note_id`** —— 外键指向 `notes.id`，`ON DELETE CASCADE`。
所以：删掉一条笔记，它的标签行会自动跟着删，不会留下孤儿数据。

一句话记法：**`notes` 是"是什么"，`note_tags` 是"归属"；两者靠 `note_id` 拴在一起。**

```sql
-- 取一条笔记和它的所有标签
SELECT n.content, t.tag
FROM notes n LEFT JOIN note_tags t ON t.note_id = n.id
WHERE n.id = 'seed_04';
```

### 为什么不是一张表（把标签塞进 notes 的一个字段）

因为一条笔记有 **0～5 个标签**。如果存成 `tags = '想法,代码'` 这种一列字符串：

- 「按标签筛选」→ 只能 `LIKE '%想法%'`，而这样 `#想法` 会误命中 `#想法很多`（前缀污染）
- 「每个标签有几条」→ 写不出来，只能把全部数据取回代码里用字符串拆
- 「标签区分大小写」→ 也没法保证

拆成关联表后，这两件事分别变成一句 `WHERE` 和一句 `GROUP BY`。

### 为什么不建第三张 `tags` 表

只有当**标签自己有属性**（颜色、自定义排序顺序）时才需要独立表 —— 那属于
`CANDIDATES.md` 里的 **C4**，本期没批准，现在建就是空壳。
等 C4 立项，加一张 `tags(tag, sort_order)` 就行，这两张表不用动。

## 二、字段类型为什么这么选（余力加练）

### `notes`

| 字段 | 类型 | 为什么 |
|---|---|---|
| `id` | `VARCHAR(32)` | **不用自增 INT**：前端已经有 `n_1727...` 这种字符串 ID，直接沿用。用自增的话，`localStorage` 里的老笔记搬上来必须重新编号，而 ID 一变，任何引用过它的地方（比如"上次翻到的那条"）就断了 |
| `content` | `VARCHAR(5000)` | 5000 是**前端 `MAX_LENGTH` 的值**。前端拦了一道，后端还要再有一道 —— 校验只在前端做等于没做（任何人都能绕过前端直接打接口） |
| `created_at` | `DATETIME(3)` | **不用 `TIMESTAMP`**：`TIMESTAMP` 有 2038 年上限，而且会随会话时区自动换算（同一份数据在不同时区连接下读出来不一样）。`DATETIME` 存什么就是什么。`(3)` 是毫秒精度，与前端 ISO 串的 `.000Z` 对齐 |
| `client_token` | `VARCHAR(64) NULL` | **Day 18 新增**。放前端每次"提交动作"生成的一个随机串，用来防**重复提交**（详情见下节）。允许 `NULL` 是有意的：种子数据、以及将来不走防重路径的写入，都不带这个值 —— 而 `NULL` 在 `UNIQUE` 索引里**互不冲突**（多行 `NULL` 可以共存），所以加这一列不会逼着历史数据都去补一个值 |
| `idx_notes_created_at` | 普通索引 | 列表默认按时间倒序（PRD 验收 1.2），这是最常用的排序字段。**没给 `content` 建索引**：搜索用 `LIKE '%词%'` 带前置通配符，索引根本用不上，建了白占空间 |
| `uk_notes_client_token` | **唯一索引**（Day 18 新增） | 防重复提交**真正的**那道闸。见下节 |

### `note_tags`

| 字段 | 类型 | 为什么 |
|---|---|---|
| `note_id` | `VARCHAR(32)` | 必须与 `notes.id` **类型完全一致**才能建外键（长度、字符集不同都会报错） |
| `tag` | `VARCHAR(50)` + **`COLLATE utf8mb4_bin`** | **这是整个表设计里最要命的一处**。PRD 规定"标签区分大小写"。MySQL 默认排序规则 `utf8mb4_unicode_ci` 是**不区分大小写**的，用它的话 `#Work` 和 `#work` 会被当成同一个标签、还会撞主键。所以单独给这一列指定 `utf8mb4_bin`（按字节比较） |
| `position` | `TINYINT UNSIGNED` | 一条笔记最多 5 个标签，`TINYINT`（0–255）绰绰有余，比 `INT` 省 3 字节。记的是标签在原文里的出现顺序，这样前端展示时不用二次排序 |
| `PRIMARY KEY (note_id, tag)` | 联合主键 | 天然保证"同一条笔记里标签不重复"（PRD 验收 2.1），不用再写去重逻辑 |
| `idx_note_tags_tag` | 普通索引 | 按标签筛选（PRD 验收 2.3）和标签计数（2.2）都从这个字段进 |

### 字符集与排名规则（表级）

| 选择 | 原因 |
|---|---|
| `utf8mb4` | 能存 emoji（`utf8` 三字节存不下，会直接报错或截断），中文更没问题 |
| 表默认 `utf8mb4_unicode_ci` | 让**正文搜索不区分大小写**（PRD 验收 3.1）。跟上面 `tag` 列的 `_bin` 是**故意相反**的两个选择 —— 同一张库里，正文要忽略大小写、标签要区分大小写 |
| `ENGINE=InnoDB` | 只有 InnoDB 支持外键和事务，MyISAM 不支持外键 |

### 为什么用 `client_token` + 唯一索引防重复（Day 18）

要防的场景：**网络卡了一下，用户以为没成功，又点了一次「保存」** ——
于是同一条笔记被提交两遍。这个坑没法靠前端解决（前端保证不了"没发出第二次"），
只能由服务端兜底。

做法分三步：

1. 前端每次**提交动作**生成一个随机串 `clientToken`（`a-z0-9_-`，8～64 位），随请求发上来
2. 库里 `notes.client_token` 建 **`UNIQUE` 索引**
3. 插入时撞了唯一键（错误码 `ER_DUP_ENTRY` / `errno 1062`）→ 返回 **`409`**，
   提示「这一条刚刚已经提交过了」

**关键点：拦住重复的不是代码里那段判断，是数据库那条唯一约束。**

反面做法是「先 `SELECT` 查有没有，没有就 `INSERT`」。它有两个问题：

- **有竞态**：查完到插入之间有时间差，两个请求同时进来会**双双通过检查**、插出两行 ——
  越是想防重复的场景，越容易撞上这种并发
- **多一次往返**：每次写入都先查一遍

唯一索引没有这个问题：判断和写入是**同一步**，由 InnoDB 保证原子性。

> 这个防重**只管"同一个提交动作重复发"**，**不管"内容一样的两次提交"**。
> 也就是说，用户真想存两条相同的笔记是可以的（只要不是同一次提交重复发）。
> 这是有意的边界：按内容判重会把"我就是想记两遍"的正常需求也误杀。

`clientToken` 之所以允许 `NULL`：种子数据和将来的批量导入都不带它，
而 `NULL` 在唯一索引里互不相等，所以不冲突。**代价**：这条防重对 `NULL` 无能为力 ——
所以只要走"用户提交"这条路径，token 就是必填（前端校验 + 服务端校验各一道）。

## 三、和前端 / 接口契约的一致性

| 一致点 | 说明 |
|---|---|
| `id` 格式 | 与 `api-contract.md` 第三节一致（字符串，服务端生成）；种子里写死成 `seed_01…` 只为幂等 |
| `tags` | 接口返回的是**数组**（`["想法","代码"]`），落在库里是 `note_tags` 的多行 —— 接口层负责把多行拼成数组（Day 17 读接口已实现），写回时反过来把数组拆成多行（Day 18 写接口，在同一个事务里） |
| `clientToken` | 只存在请求体里，不对应返回字段（返回的是服务端生成的 `id`）。库里落成 `notes.client_token`，仅用于唯一索引判重，**读接口不返回它** |
| 时间 | 库里一律 **UTC**；"显示成什么时区"由前端 `formatTime()` 负责，库里不做换算。前端 localStorage 里既有的就是 UTC ISO 串 |
| 上限值 | `content` 5000 / 每笔记最多 5 个标签 —— 与前端 `MAX_LENGTH`、`MAX_TAGS` 同一个数，改动时必须两边一起改 |

### 一次被自检拦下来的错误（Day 17，写在这里免得再犯）

`queries-read.sql` 第 ⑥ 段原先用 `GROUP_CONCAT(... SEPARATOR '\u001f')` 拼标签。
**这是错的**：`\u001f` 是 JS / Python 的转义写法，**MySQL 不认**，
遇到不认识的转义会丢掉反斜杠 —— 于是分隔符变成字面量 `u001f`，
拼出来是 `想法u001f代码`，而且**不报任何错**。

顺带两个同源问题：标签是用户自己起的名，逗号 / 竖线 / `#` 都可能出现，
"挑一个不会出现的分隔符"本质上是赌；而且 `GROUP_CONCAT` 受 `group_concat_max_len`
限制（默认 1024 字节），超了会**静默截断**。

→ 现在改成**两句 SQL**（先筛笔记 id，再按这批 id 取全部标签）。
这样"筛标签时标签不会被筛选条件吃掉"这条正确性变成了**结构上**保证的，
不再依赖分隔符挑得好不好。实现见 `cloudbase-functions/notes/index.js`。

**没验证的两处已知风险**（真跑时优先看这两条）：
1. `ON DUPLICATE KEY UPDATE ... VALUES(col)` 在 MySQL 8.0.20+ 会报**告警**（不是错误）。
   写成老式是为了兼容可能的 5.7 实例；确认是 8.0 后可改成 `AS new` 新写法。
2. `TINYINT UNSIGNED`、`DATETIME(3)` 需要 MySQL 5.6+，CloudBase 的实例满足，但如果你创建的是
   兼容模式/其他引擎，可能要在控制台里换成对应类型。

## 五、命名与书写约定

- 表名、字段名一律**小写 + 下划线**，不用驼峰（避免 Windows 上大小写不敏感、Linux 上敏感导致的诡异问题）
- 时间字段统一叫 `created_at` 这种 `_at` 结尾
- 关联表命名 `主表_从表`（`note_tags`），一看就知道它在连接谁
