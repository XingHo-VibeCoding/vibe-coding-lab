## 什么时候跑

改了这些东西之后**必须先跑一次再提交**：

- `api.js`（真实接口的取数、信封拆解、形状校验、出错提示）
- `app.js` 里 `bootstrap()` 那段"选哪个数据来源"
- `api-contract.md` 的成功/失败信封（C 段的断言照着契约写死）

```bash
node skills/notelab-api-wiring/check.cjs
```

要求 **Node 22+**（自带 `fetch`）。**零依赖**，也不需要浏览器和数据库。
记录本次结果：全绿（Day 20 起 **24/24**）再提交。

## 为什么它值得单独一个 skill

前端已经有 `notelab-filter-check`（筛选/渲染），云函数有 `notelab-api-check`（服务端）。
**中间那一截"页面怎么去网上拿数据"两头都不管** —— 而它恰恰是最容易出事的地方：
同一句"取不到数据"背后是三种完全不同的病，认错了就白查半天。

所以这个 skill 只盯一件事：**数据从接口到页面的这一段**。

| 段 | 验什么 | 为什么非有不可 |
|---|---|---|
| 一 | 地址怎么配的（含"不配就不启用"） | 这是本次改动的**安全底线**：没配地址时页面行为必须与改动前完全一致，不能动到用户已存的笔记 |
| 二 | 网关两种信封都能拆 | 部署前无法确定 CloudBase 拆不拆 `{statusCode, headers, body}`，所以两种都得能活 |
| 三 | 形状对不上就报错 | "拿到什么算什么"是最糟的：页面会显示一片空白，还不报错 |
| 四 | **出错提示有没有告诉用户去看哪里** | 写"出错了"等于把排查成本推给用户。今天的主题就是"怎么认出问题出在哪" |
| 五 | 本机起真服务，用真 `fetch` 打真请求 | 纯函数全绿但 fetch 参数写错（ Credentials / header / 路径拼错），照样取不到数据 |

## 明确**没**验到的（不要当成已验过）

脚本每次都会打印，其中第一条是**本机永远验不了**的：

1. ★ **浏览器是否真的放行跨域（CORS）**。CORS 是**浏览器**执行的规则，
   Node 的 `fetch` 不执行它 —— 本机怎么跑都验不出来。
   只能部署后用真浏览器 + F12 验（看 Console 有没有带 CORS 的红字）。
2. CloudBase 的 HTTP 访问服务到底拆不拆信封（二段两种都认，真跑才知道是哪种）。
3. 公网 URL 与静态托管是否可达（需要环境 ID）。
4. 页面在真浏览器里渲染真实数据的样子（需要环境 ID）。

> 第 1 条是这里最容易自欺的地方：本机 24/24 全绿，
> **完全不代表跨域已经配好了**。跨域要等真浏览器说了才算。

## 三种"取不到数据"的分辨法（写在这里，免得每次重新推一遍）

| 病 | F12 里的样子 | 该改哪里 |
|---|---|---|
| **A. 跨域没过** | Console 有带 `CORS` / `blocked by CORS policy` 的红字；Network 那条可能是 200 但 Response 空 | **服务端**响应头（`cloudbase-functions/notes/http.js`）。前端改任何代码都没用 |
| **B. 地址不对 / 服务不在** | Network 那条 404 / 502，或者根本连不上 | 核对环境 ID 与路径 `/api/notes` |
| **C. 形状不对** | 请求 200、Response 有内容，但页面空白或报"形状不一致" | 看 Response 的 JSON，对照 `api-contract.md` |

`api.js` 里 `corsHint()` 的措辞就是照这张表写的，D 段的断言盯的就是它。
